# tinvist

Торговый агент для российского рынка поверх **[T-Bank Invest MCP](https://developer.tbank.ru/invest/mcp)**.

Модель работы — **гибрид с подтверждением**: стратегия и LLM *предлагают* сделку,
человек *подтверждает* (в терминале или Telegram), и только после этого агент
исполняет заявку. Ни один ордер не уходит брокеру без явного «да», а на боевом
контуре реальные деньги защищены тремя независимыми предохранителями.

---

## Что это и как устроено

T-Bank Invest MCP — это готовый MCP-сервer от Т-Банка (`https://invest-public-api.tbank.ru/mcp`),
отдающий 68 инструментов: аналитика, портфель, котировки, заявки. tinvist —
клиент над ним со своей стратегией, риск-контролем и подтверждением.

```
Данные/сигналы   →  Стратегия + LLM   →  Guard-лимиты  →  Подтверждение  →  Исполнение
 (котировки,          (TradeProposal)      (риск-чек)      (CLI / Telegram)   (ордер)
  свечи, портфель)                                                                │
                                                                                  ▼
                                                                            Audit-лог (JSONL)
```

### Два контура (`BACKEND`)

| Контур | Транспорт | Деньги | Назначение |
|---|---|---|---|
| `sandbox` | REST `SandboxService` | ненастоящие | отладка чтения **и** исполнения |
| `prod` | MCP | **реальные** | чтение сейчас, торговля позже |

> **MCP работает только с боевым контуром** — sandbox-токен там не авторизуется.
> Поэтому песочница ходит напрямую в REST `SandboxService`, мимо MCP. Биржевые
> данные (котировки, свечи, справочник инструментов) в обоих контурах берутся
> через MCP prod — они одинаковы.

## Быстрый старт

```bash
npm install
cp .env.example .env        # впиши токены (см. «Конфигурация»)

npm run cli -- accounts     # счета активного контура
npm run cli -- portfolio    # портфель
npm run cli -- find SBER    # поиск инструмента (ticker, uid, лот)
npm run cli -- quote <uid>  # последняя цена
```

Проверка типов: `npm run typecheck`. Сборка: `npm run build`.

## Команды

Формат: `npm run cli -- <команда> [аргументы]`.

### Данные (через активный `BACKEND`)

| Команда | Описание |
|---|---|
| `accounts` | Список счетов |
| `portfolio [accountId]` | Портфель (по умолчанию — первый счёт) |
| `quote <instrumentId>` | Последняя цена инструмента (UID) |
| `status [accountId]` | Сводка: капитал, кэш, позиции с нереализ. P&L, просадка, сделки за день |

### Торговля (полный конвейер guard → подтверждение → исполнение)

| Команда | Описание |
|---|---|
| `order <тикер\|uid> <buy\|sell> <лоты> [лимит-цена] [accountId]` | Ручная заявка |
| `propose <тикеры,через,запятую> [accountId]` | LLM предлагает сделки, каждая идёт через тот же конвейер |
| `rsi <тикеры,через,запятую> [accountId]` | Детерминированная RSI mean-reversion стратегия (без LLM) |
| `loop <тикеры,через,запятую> [accountId]` | Планировщик: гоняет стратегию по расписанию (см. ниже) |

Примеры:

```bash
npm run cli -- order SBER buy 1              # рыночная покупка 1 лота
npm run cli -- order SBER buy 1 300          # лимитная по 300 ₽
npm run cli -- propose SBER,LKOH,GAZP        # предложения от LLM
```

### Интроспекция MCP (всегда prod-токен)

| Команда | Описание |
|---|---|
| `find <запрос> [instrumentKind]` | Поиск инструмента (по умолчанию акции) |
| `list-tools` | Все MCP-инструменты |
| `describe <tool>` | JSON-схема входа инструмента |
| `call <tool> '<json>'` | Сырой вызов инструмента (отладка) |

## Движок предложений (`propose`)

Собирает контекст (портфель + свободный кэш + по каждому тикеру: цена и
30-дневные дневные свечи) и просит LLM вернуть 0..N предложений в строгом
структурированном виде. Провайдер переключается через `LLM_PROVIDER`:

- **`gigachat`** (по умолчанию) — Sber GigaChat. Ключ `GIGACHAT_AUTH_KEY`
  (Basic) из ЛК GigaChat API. OAuth с кэшем токена → chat/completions;
  structured output через строгий JSON-промпт + валидация zod с одним повтором.
- **`anthropic`** — Claude (`claude-opus-4-8`, adaptive thinking, нативный
  structured output через `messages.parse`). Ключ `ANTHROPIC_API_KEY`.

LLM только *предлагает*. Каждое предложение проходит guard-лимиты и
подтверждение — движок не может исполнить сделку в обход конвейера.

### Детерминированная стратегия RSI (`rsi`)

`src/strategy/rules/rsi.ts` — mean-reversion без LLM: RSI(14) считается из
дневных свечей (Уайлдер). Предсказуема и воспроизводима; результаты идут через
тот же конвейер (guard → подтверждение → исполнение).

**Входы:** покупка 1 лот при `RSI ≤ RSI_OVERSOLD`, если позиции нет и сделка
влезает в кэш и `MAX_ORDER_RUB`.

**Выходы** (управление открытой позицией, проверяются на каждом запуске):
продажа всей позиции при `RSI ≥ RSI_OVERBOUGHT`, **или** тейк-профит
(`цена ≥ вход·(1+RSI_TP_PCT%)`), **или** стоп-лосс (`цена ≤ вход·(1−RSI_SL_PCT%)`).
Это «программные стопы», вычисляемые при каждом прогоне — работают в обоих
контурах (в песочнице биржевые стоп-ордера недоступны). Средняя цена входа
берётся из портфеля.

**Дивидендный фактор** (`DIV_ENABLED`, данные из `invest_get_share_dividends`):
- **Вход** имеет приоритет над RSI: покупка, если до отсечки (`lastBuyDate`)
  ≤ `DIV_ENTRY_WINDOW_DAYS` дней и дивдоходность ≥ `DIV_MIN_YIELD`% (захват
  дивиденда + типичный разгон к отсечке).
- **Выход**: `DIV_SELL_AFTER_PAYMENT=true` — держим через отсечку, продаём после
  `paymentDate` (твой сценарий «продать после выплаты»); `false` — продажа перед
  отсечкой (skip-gap, без дивиденда, но без гэпа).

Пороги настраиваются через env (`RSI_*`, `DIV_*`).
Иначе — пропуск (стратегия не торгует без сетапа).

> Дивиденд — лишь один фактор. Дальше сюда же ложатся: фундаментал
> (`invest_get_asset_fundamentals` — P/E, ROE, долг), календарь отчётностей
> (`invest_get_instrument_reports`), новости/сентимент (`invest_get_news`),
> стакан/объёмы. Каркас стратегии расширяется добавлением новых факторов-сигналов.

> ⚠️ Ни одна стратегия не гарантирует доход. На малом счёте (напр. 3000 ₽)
> комиссии и «шаг лота» съедают преимущество, а песочница идеализирована
> (мгновенное исполнение по последней цене, без спреда и проскальзывания) —
> прибыль в песке ≠ прибыль на реале. Это каркас с риск-контролем, не «грааль».

## Планировщик (`loop`)

`src/scheduler.ts` — встроенный цикл: каждые `LOOP_INTERVAL_SEC` секунд гоняет
RSI+дивидендную стратегию, чтобы входы/выходы, стопы и kill-switch проверялись
**регулярно**, а не только по ручному запуску. Уважает часы биржи
(`LOOP_MARKET_HOURS_ONLY`, окно `LOOP_START_HOUR_MSK`–`LOOP_END_HOUR_MSK` МСК,
только будни), устойчив к сбоям (ошибка одного цикла не роняет петлю),
останавливается по Ctrl-C / SIGTERM.

```bash
npm run cli -- loop SBER,GAZP,MTSS <accountId>
```

Для постоянной работы запускай под супервизором (pm2 / systemd / docker), а
подтверждение переключи на Telegram (`APPROVAL_CHANNEL=telegram`) — тогда цикл
шлёт карточки в чат и ждёт ✅/❌ на каждый сигнал.

**Ежедневная сводка** (`DAILY_REPORT_ENABLED`): раз в день после
`REPORT_HOUR_MSK` (по умолчанию 19:00 МСК) планировщик шлёт в Telegram отчёт
`status` — капитал, позиции с нереализ. P&L, просадку, сделки за день.

> **Важно:** «программные» стопы (RSI/тейк/стоп) и kill-switch срабатывают
> только в момент тика. Между тиками позиция не защищена — интервал стоит
> держать небольшим (напр. 5–15 мин) в торговые часы. Для защиты 24/7 (в т.ч.
> когда агент выключен) нужны **биржевые стоп-ордера** (`invest_create_stoporder`,
> prod-only).

## Безопасность

Реальная отправка ордера на **prod** возможна только когда сняты **все три**
предохранителя одновременно:

```
BACKEND=prod  +  DRY_RUN=false  +  ALLOW_REAL_TRADING=true
```

Любой невыставленный флаг → dry-run (заявка логируется, но не отправляется).
Песочница исполняет при `DRY_RUN=false` (деньги ненастоящие).

**Guard-лимиты** (проверяются до вызова брокера, блокируют сделку):

| Лимит | Что проверяет |
|---|---|
| `MAX_ORDER_RUB` | Максимальная сумма одной сделки |
| `MAX_POSITION_SHARE` | Максимальная доля инструмента в портфеле (только на покупку) |
| `MAX_DAILY_TURNOVER_RUB` | Дневной оборот заявок (по audit-логу) |
| **Гейт прибыльности** | Блокирует покупку, если её цель (тейк) не покрывает round-trip издержки: `targetPct ≥ (2·COMMISSION_PCT + SLIPPAGE_PCT)·MIN_NET_EDGE_RATIO`. Убивает убыточный по комиссии скальпинг |
| **Лимитные заявки** (`USE_LIMIT_ORDERS`) | Marketable-limit по стакану: потолок цены = крайний уровень в пределах `LIMIT_SLIPPAGE_CAP_PCT` + FILL_AND_KILL. Заливается по лучшей цене, проскальзывание ограничено, не оставляет висящих заявок |
| **Фильтр ликвидности** (`MAX_SPREAD_PCT`) | Не входит в бумаги со спредом шире порога (дорогое проскальзывание). Применяется к входам |
| **Circuit breaker** (`VOLATILITY_ENABLED`, `MAX_INTRADAY_RANGE_PCT`) | Не входит при аномальном внутридневном размахе (флэшкрэш/каскад): размах (max high − min low)/last по 5-мин свечам за час выше порога → пропуск входа |

**Сохранение капитала** (защита от разорения; применяется к покупкам,
продажи-сокращение риска всегда разрешены):

| Механизм | Что делает |
|---|---|
| `MAX_DRAWDOWN_PCT` | **Kill-switch**: запоминает пик капитала (HWM в `data/equity-hwm.json`); при просадке ≥ X% от пика блокирует новые покупки |
| `EQUITY_FLOOR_RUB` | Жёсткий пол: ниже этого капитала покупки запрещены |
| `MAX_TOTAL_EXPOSURE_PCT` | Держит денежную подушку (макс. доля в бумагах) |
| `MAX_OPEN_POSITIONS` | Ограничивает число открытых позиций |

> Это снижает риск **разорения** (survival), но не устраняет убытки: гэпы,
> проскальзывание и движения «в неторговое время» всё равно бьют по счёту.
> Программные стопы срабатывают только при запуске стратегии — для реальной
> защиты нужен запуск по расписанию и (на проде) биржевые стоп-ордера.

**Audit-лог** — `audit/trades.jsonl`, append-only, по одной строке на событие:
`proposal → guard → approval → execute → result`. Ретраи применяются только к
чтению; создание заявки **не** повторяется (защита от задвоения).

### Канал подтверждения

- `APPROVAL_CHANNEL=cli` (по умолчанию) — y/N в терминале.
- `APPROVAL_CHANNEL=telegram` — карточка сделки с inline-кнопками ✅/❌;
  агент long-polling'ом ждёт нажатия (таймаут 5 мин → безопасный отказ).
  Нужны `TELEGRAM_BOT_TOKEN` + `TELEGRAM_APPROVER_CHAT_ID`.
  ⚠️ У бота **не должно быть webhook** (иначе `getUpdates` → 409).

### Токены — где хранить

`.env` в `.gitignore`. Токены дают доступ к реальному счёту: не коммить,
не логируй. Prod-токен полного доступа = агент технически способен на настоящую
сделку, единственная преграда — предохранители выше.

## TLS

Сертификаты T-Invest и GigaChat выпущены через **Russian Trusted Root CA**
(Минцифры), которого нет во встроенном наборе Node → без него `fetch failed`
(`SELF_SIGNED_CERT_IN_CHAIN`). Цепочка лежит в `certs/russian-trusted-ca.pem`,
npm-скрипты подхватывают её через `NODE_EXTRA_CA_CERTS`. Проверка TLS **не
отключается**.

## Структура

```
src/
  config.ts              конфиг + zod-валидация + предохранители
  domain.ts              доменные типы + парсеры денег (MCP {value} / REST {units,nano})
  cli.ts                 CLI-диспетчер
  mcp/client.ts          MCP-клиент (StreamableHTTP + Bearer)
  backends/              торговые контуры
    types.ts             интерфейс TradingBackend
    mcp.ts               prod (MCP)
    sandbox.ts           sandbox (REST SandboxService)
    factory.ts           выбор по BACKEND
  instruments/
    resolve.ts           поиск инструмента (uid, лот)
    marketdata.ts        свечи (контекст для LLM)
  strategy/
    types.ts             TradeProposal
    engine.ts            LLM-движок предложений
    run.ts               один цикл RSI-стратегии (общий для rsi/loop)
    rules/rsi.ts         RSI mean-reversion + дивидендный фактор
  scheduler.ts           планировщик (команда loop): часы биржи, устойчивость
  llm/                   переключаемый LLM
    schema.ts            общая zod-схема ответа
    types.ts             интерфейс ProposalLLM
    anthropic.ts         Claude (messages.parse)
    gigachat.ts          Sber GigaChat (OAuth + JSON)
    factory.ts           выбор по LLM_PROVIDER
  safety/
    guards.ts            guard-лимиты + сохранение капитала
    equity-state.ts      пик капитала (HWM) для drawdown kill-switch
  audit/log.ts           append-only JSONL + дневной оборот
  approval/              подтверждение
    types.ts             интерфейс Approver
    cli.ts               терминал (y/N)
    telegram.ts          inline-кнопки + long-polling
    factory.ts           выбор по APPROVAL_CHANNEL
  execution/executor.ts  оркестратор: портфель → guard → аудит → подтверждение → отправка
  util/retry.ts          ретрай транзиентных сбоев (только чтение)
certs/russian-trusted-ca.pem   CA для TLS
audit/trades.jsonl             журнал сделок (gitignored)
```

Стек: TypeScript + Node 20+, `@modelcontextprotocol/sdk`, `@anthropic-ai/sdk`,
`zod`, `dotenv`. Запуск через `tsx`.
